### §1.4 由 P0.10 引出的新事实: 三轨 prompt 存在 ~14.8% 去重重合 (影响稳健性论证的解读)

每模型的**请求数** = 242,000 行 × 3 轨 = **726,000**, 而其**缓存条目数**实测仅 **~618,500** ⟹ 约 **107,500 (14.8%)** 的请求落在**同一个 cache_key** 上。缓存键 = `model_id + prompt 文本 + prompt_version + temperature`, 故这必然意味着**不同轨产生了逐字节相同的 prompt**。

**成因 (量级吻合, 但非唯一来源, 未穷尽)**: `content_ss` 在无严格同句共现时**回退为全文 body**, 与 `content_full` 相同 ⟹ 该行的 ss 与 full 是同一个 prompt。CLAUDE.md 载 stage 13 严格同句 (radius=0) 零共现率 = **14.27%**, 与实测 14.8% 量级吻合 (242,000 × 14.27% ≈ 34,533 行仅解释约三分之一, 余下差额疑来自 ctx 轨在窗口覆盖全文时同样退化, **未定谳**)。

**性质**: 这是 CLAUDE.md 已声明的回退设计 (「无同句共现 → `content_ss`=全文 body + `ss_is_fallback`=True」) 的**必然算术后果**, **不是缺陷**。

**但对解读有实质含义, 须披露**: 在这部分行上, ss 轨与 full 轨消费的是**同一个 LLM 响应**, 三轨不再是三个独立观测 ⟹ 「三轨互为稳健性 / 三角验证」的有效样本小于名义样本。日志现有的 triple-gate 与 verified 率诊断**看不出**这一点 (log:70 只报 `content_ss` 非空 100%, 未报其中多少是 fallback)。建议纳入 §7-Q5 与手稿披露。

## §2 定谳缺陷

> 严重度经 §8 自审重排: **D5 由「中」升「严重」** (它才是墙钟与成本的真正大头), **D3 由「严重」降「中」**, **D2 由「定谳」降「机理确凿·幅度待定谳」**。

### D1 【严重·阻塞复现】弃票不入缓存 ⟹ 离线 `$0` 复现永久不可达, 且离线跑是 **hard-fail 崩溃**而非降级

**现象**: 本次 267 次弃票对应的 (model, prompt) 格**永不写入** `_llm_cache.db`。下次任何一跑对这些格都必然 miss。

**根因 (代码级)**:
- `tone_llms.py:735-749` — 200 但空/不可解析/缺 `is_bank_fintech_news` 键 → `continue` 重试, 注释明写「**绝不 cache.put**」; 80 次耗尽后 `return ... None`, 全程无任何持久化。
- `tone_llms.py:695-700` — `LLM_OFFLINE` 下 miss 直接 `raise LLMCacheMissError`。

**「hard-fail 崩溃」已终验 (v3, 逐层查完调用链, 此前仅为推断)**:

| 层 | 位置 | 是否捕获 |
|---|---|---|
| 抛出点 | `:696` `raise LLMCacheMissError` | — |
| 消费循环 | `:950-951` `for coro in asyncio.as_completed(...)` | 无 try |
| 事件循环驱动 | `:2422-2427` `try: run_until_complete(...) finally: ...` | **try/finally, 无 except** |
| `main()` 内唯一 try | `:2358` | 是**只读诊断块** (注释自陈「任何诊断异常绝不拖垮阶段」), 不含 LLM 调用 |
| CLI shim | `21_tone_llms.py` `if __name__ == "__main__": main()` | 无 catch |

⟹ 异常一路冒泡到进程顶层, **未捕获异常 → 非零退出码 → 阶段真崩**。断言确凿, 非推测。

**影响**:
1. 直接冲突 CLAUDE.md 铁律「三轨缓存 0 miss 即可 `NEWS_PROCESS_LLM_OFFLINE=1` 离线 `$0` 字节级复现」——**0 miss 状态在概率上不可达**。
2. 离线复现不是「部分漂移」而是**阶段直接崩掉**, 复现包 / golden 重生链条被硬阻塞。
3. 弃票集合疑似**非固定**: memory 载上一跑 ~300–500 votes/轮, 本次 267 → 提示是随机抖动而非固定顽固行。⚠ 上一跑日志已被覆盖, **此点未定谳**, 定谳办法见 P1.5。

**整改**: 新增**独立**弃票登记表 `_llm_dropped_votes` (同库不同表, 键结构同构: `model_id + prompt_hash + prompt_version + temperature`; 存 `reason` / `first_seen` / `attempts` / `http_status` / `permanent`)。
- 写入侧: `fetch_llm_async` 返回 `None` 前登记一次。
- 读取侧: `LLM_OFFLINE` 且主缓存 miss 时先查该表 —— 命中则返回 `None` 票 (等价复现当次弃票) 并 loud WARNING, **不 raise**; 仍未命中才 raise。
- ⚠ 铁律不变: 该表**绝不**参与在线路径的正常命中; 主缓存 `_llm_cache.db` 只装通过 `_is_cacheable_llm_response` 的好响应, 原设计意图零妥协。

**⚠ 实施纪律 (v3 新增, 因 §1.3 发现库已 98.9 GB)**:
1. **只允许 `CREATE TABLE` 新表**。**严禁**对 `llm_cache` 主表做 `ALTER TABLE` / `CREATE INDEX` —— 98.9 GB / 2415 万页上会长时间持锁并需要等量临时空间, 且该库被 stage 15/25/26/27/40/48 共用, 锁库将连坐多阶段。
2. 该库为 WAL 模式, 新表的并发读写安全。
3. **本方案会使一条既有不变量失效, 必须同步改**: `:2430-2433` 注释称「离线模式下 miss 会先 raise, 故此处能打印即代表零 miss」—— 弃票登记表放行后, 离线跑将出现 `misses = 弃票数 > 0` 却正常跑完。判据须改写为「**真 miss = 0** 且全部 miss 均在弃票登记表中有据可查」。这也是对 CLAUDE.md「缓存全命中 ⟺ 离线 $0 复现」铁律判据的实质修订 → 并入 §7-Q2 一并裁定。

### D5 【严重·成本+墙钟】gemini31 独占 264/267 弃票, 每格空转 80×10s; 且它是平局重试 63% 墙钟的真凶

**日志自身已发出该警告却无人执行**: log:492「⚠ 若失败集中于单一模型/单一轨 …… **建议核查网络/限流后重跑**」——事实正是极端集中于单一模型。

**代价 (两处, 第二处为自审新发现)**:
1. **首跑长尾**: 263 格 × 80 次 × 10s ≈ 800s/格, 正是 log:95(95%, 15:36:23) → log:364(100%, 15:55:08) 之间 **19 分钟**长尾的成因。调用量 263 × 80 = **21,040 次**。
2. **卡死平局重试第 1 轮** (新发现): 平局重试第 1 轮耗时 **1033s = 17.2 分钟 = 整个平局重试 1636s 的 63.1%**。原因是该轮内有 2 个 gemini 请求走满 80×10s (log:367 16:12:03 / log:368 16:12:50 的弃票记录即是它们), 而 `:1062` 的逐轮 barrier **必须等最慢请求**。⟹ 平局重试的墙钟大头不是「轮次空转」(D3), 而是 D5 卡住 barrier。

**投票影响**: 264 个 (行×轨) 的多数决从 3 票退化为 2 票, 占 726,000 个 (行×轨) 的 0.036%。

**计费**: 空 completion 是否计费**未经证实** (通常 input token 计费、output 为 0)。⚠ 标注为**待账单核实**, 不作为立案依据 —— 本项即使零计费, 墙钟代价 (19 分 + 17.2 分) 也已足够立案。

**待查根因 (三选一, 需实测定谳)**: ① yunwu 网关对 gemini 的 `response_format: json_object` 支持退化; ② 模型侧对特定长文本返回空 completion; ③ 高并发下网关截断响应体。

**整改**: P1.2 探针定谳后, 对「200 空响应」这一**确定性**失败型设专用低重试上限 (与瞬时网络故障的 80 次分开)。见 §7-Q3。

### D4 【中·排障误导】400 内容风控被日志报成「连续 80 次请求**等待超过时限**」

**现象**: log:96-101 —— 3 条 `ERROR API 错误 400: Content Exists Risk` 各紧跟一条 `连续 80 次请求等待超过时限，该次结果将从投票中排除`。

**根因**: `tone_llms.py:806-819` 非 (429/5xx/auth) 状态码走 `logger.error(...)` 后**直接 `break`**, 但**未更新 `last_failure_reason`** → `:840`/`:420` 打印的是该请求**上一次**失败原因 (此处为 `:821` 的 TimeoutError 文案) 的陈旧残留。

**旁证 (证明真的只调了 1 次而非 80 次)**: 若真重试 80 次应有 80 条 `ERROR 400`; 全日志 `ERROR` 仅 **3** 条, 与 3 个弃票 1:1 ⟹ 400 确为 fail-fast, 文案纯属失实。

**影响**: 把「内容风控永久拒绝, 重试无解」误导成「超时/网络问题, 调大超时或重跑可解」, 直接指向错误的排障方向。同时 `:837-838` 把永久性 400 记为 `note_transient_failure`(**瞬时**故障), 语义错误。

**整改**:
1. `break` 前赋 `last_failure_reason = f"HTTP {resp.status} 不可重试错误 (已 fail-fast, 未重试): {摘要}"`。
2. 增设 `note_permanent_failure`, 与瞬时故障分开计数、阶段末尾分列汇总。
3. 该类格写入 D1 登记表并标 `permanent=1`, 后续跑直接跳过。
