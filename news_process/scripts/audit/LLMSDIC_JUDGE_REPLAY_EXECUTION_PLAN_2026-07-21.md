## 0. 白话总览（要干哪些事情）

大白话说，这件事分五步：

1. **先承认一个事实**：盲审的缓存**已经存在**（2026-07-10 上线的 `llm_cache.py`，main=7153e55a）。13 个大模型对每批词的原始回答，早就按「模型+温度+批次内容+重试序号」逐条存进了本目录的 SQLite 缓存库。再跑一遍时命中缓存就不花钱、不调 API。**所以本计划不是"从零加缓存"，而是把"缓存了"升级成"可证明的完美复现"。**
2. **给每次跑发一张"体检报告"**：现在的问题是——如果首跑中某个模型连续失败被跳过、或某批词重试耗尽，程序会**悄悄给这批词全记 0 分**，而且这些失败**不会进缓存**（缓存里出现"空洞"）。下次重放走到空洞就对不上了。整改后，每次跑完程序会明确宣告："本次跑 0 降级，**可以**逐字节复现" 或 "本次跑有 N 个任务走了降级路径，**不可**复现，明细如下"。
3. **给每次跑留一张"存根"（盲审清单 manifest）**：跑完后把"这次盲审到底审了哪些词、怎么分批、每个模型每批实际用了缓存里的哪几条记录"写成一个 JSON 文件落盘。这就是复现的凭证——以后任何人拿着这张存根就能核对。
4. **做一个"验钞机"（缓存覆盖验证器）**：一个独立小脚本，读上面的存根，把每个缓存键重新算一遍、逐条去缓存库里查。全部命中 → 盖章"可离线 $0 复现"；有缺 → 列出缺哪几条。这是主项目 `verify_stage21_cache_coverage` 的镜像。
5. **真刀真枪验收一次**：设 `LLMS_DIC_OFFLINE=1`（离线模式，缓存缺了就报错、绝不偷偷调 API 花钱）重跑一遍，对比两次产出的判别 sheet——每个词、每个模型的分数和理由必须一模一样。对得上，"完美可复现"才算落地。

一句话：**缓存已有，本计划补的是"证明复现"的三件套——体检报告、存根、验钞机——再用离线重跑实测验收。**

## 2. 缺口清单（为什么现在还不算"完美可复现"）

- **G1 降级路径产生不可见的假 0 票 + 缓存空洞**（最重要）。**五**条路径都会让 `judge_batch` 返回全 0 行并**静默**并入最终词典：
  1. `_call_llm_with_retry` 硬失败耗尽重试返回 None（该 try 无缓存条目）；
  2. `_model_health.should_skip` 命中（模型被健康追踪器跳过，整批 0 分且零缓存）；
  3. `_shutdown_event`（Ctrl+C / 全局重试上限触发）；
  4. `MAX_JUDGE_RETRIES` 耗尽后的部分采纳/全 0 兜底；
  5. **离线缓存空洞**（`LLMCacheMissError` 捕获路径 `00_LLMs_for_dic.py:880-884`：置 shutdown 后返回全 0——终审补入，原计划漏计此第五条）。
  这些 0 分与模型真实判 0 在产物里**不可区分**，且离线重放走到空洞会中断——首跑不干净则复现承诺整体作废，而目前**没有任何机制告诉你首跑干不干净**。
- **G1b 聚合层空洞：executor break 丢弃已完成结果**（终审补入）。主循环 `main()` 在 shutdown 时 `break`（`00_LLMs_for_dic.py:1399-1401`），**已经算完但尚未收集**的 future 结果被整体丢弃；缺席的 (model, keyword) 在构建 DataFrame 时经 `model_results[model].get(kw, [0, ""])`（`:1427`）静默补 0。这条通路发生在 `judge_batch` **外部**——单靠 judge_batch 内的降级计数器**看不见它**，可能产出「计数器全 0 → 误判 ✅ 可复现」的假阴性。判决必须附加**全格覆盖对账**（见 P1 修订）。
- **G1c 生成阶段同病，且直接打断全链重放**（终审补入）。`fetch_batch` 有完全同构的降级路径（硬失败返空列表 `:764`、健康跳过 `:738`、shutdown `:748`、离线 miss `:757-762`）。首跑生成任务失败 = 该 rep 无缓存条目 **且词表本身少词** → 全链离线重放要么 `LLMCacheMissError` 中断、要么复现出**不同的词表**（批次整体移位、判别缓存全 miss）。**处置（2026-07-21 用户铁律：严禁动生成阶段）**：不给生成阶段装任何 instrumentation；D2 的 `--from-manifest` 模式升格为盲审复现的**正典通道**（从 manifest 冻结词表直接重放，彻底不依赖生成阶段干净性），全链重放降为机会性验证（词表哈希对不上或撞缓存空洞即改走 D2，见 P4）。
- **G2 无复现凭证**。盲审的缓存键依赖运行期词表（整批词在 prompt 里），跑完不留清单，事后无法枚举"这次跑该有哪些缓存条目"，也就无法验证覆盖。
- **G3 无覆盖验证器**。主项目有 `verify_stage21_cache_coverage`，本目录没有镜像——"可复现"目前只是口头承诺，没有可执行的证明。
- **G4 无验收记录**。从未做过"在线首跑 vs 离线重放"的 A/B 逐字节比对，"完美可复现"没有实测背书。
- **G5 健康追踪器状态不落盘**（已知、接受）。`_model_health` 是纯内存状态；首跑有模型被跳过时天然不可复现——整改方向不是持久化它，而是让 G1 的报告把这种跑**判为不可复现**并醒目宣告。

### P3 — 缓存覆盖验证器（新脚本 `verify_judge_cache_coverage.py`）

- 独立 CLI，放在 `LLMs_for_FinTech_dic/` 目录：
