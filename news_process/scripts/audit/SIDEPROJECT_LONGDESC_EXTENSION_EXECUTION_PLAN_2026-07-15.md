## 0. 背景与动机

`config/codebook_longdesc/` 体系(655 个家族长文, ≥1000/≥5000 汉字门槛, 强制学术引用, `admit_new_dois.py` 白名单闸)目前**仅覆盖 news_process 主项目**(`40/46/51_panel_*.dta`)。

`company_listed_bank`(银企共现面板, 主面板20固定列+加权测度列+7替代权面板)与 `company_tax_bank`(税调×银行共现, 同构)是两个**独立、已完工**的侧线管道, 各自已有一份表格型 `*_cooc_panel_codebook.md`(216 行 / 355 行), 内容详实(数据谱系、门控双宇宙、局限清单、互验报告链接等), 但**不是**长文引文格式 —— 没有逐变量的 `## VAR:` 学术引用小节, 也不接入 `check_longdesc_whitelist.py` / `admit_new_dois.py` 闸。

本计划评估的问题: **是否值得、以及如何**把这两个侧线项目升级到与主项目同等的长文引文体系。

## 1. 范围盘点

| 项目 | 现有 codebook | 变量行数(逐列表) | 新增(七/四权面板等衍生) |
|---|---|---|---|
| company_listed_bank | `company_bank_cooc_panel_codebook.md`(216行) | 主面板固定列 20 + 加权测度列(通式, 非逐列枚举) + pair 长表 10 列 | 七替代权面板(loan/branch/board/supervisor/exec/dsg/shareholder), 列名同构(`cw_/ce_{基名}_{track}`) |
| company_tax_bank | `company_tax_bank_cooc_panel_codebook.md`(355行) | 类比结构, 120 个表格行(`grep -c '^|'`口径, 含表头/分隔符, 非精确变量数) | 待核实是否也有替代权衍生面板 |

⚠ **口径不一致待修正**: 上表两行的"变量行数"统计方法不同(listed_bank 按人工识别的固定列/pair列分类计数, tax_bank 按 grep 行数粗估、含表头噪声), 不可直接横向比较。P1 前须对两项目各自重新做精确逐列清点(区分:固定列 / 通式衍生列 / pair 或长表列 / 说明性表格行), 本表当前仅供数量级参考, 不作为规模估算的最终依据。

**关键差异 vs 主项目**: 两侧线的加权测度列是**通式生成**(`cw_X_t = Σ...`, X 取自银行×年面板任意数值列), 不是像主项目那样离散命名的 655 个"家族"。逐列枚举会产生**远超主项目规模**的变量数(每个可加权的银行×年测度列 × 3 轨 × 2 臂(cw/ce) × 8 权重版本 = 组合爆炸), 这是本计划必须先解决的**范围界定问题**, 而非直接照搬主项目"一家族一长文"的模式。

## 2. 建议的范围界定(供用户拍板)

不建议逐一枚举全部加权测度列组合(数千甚至上万个组合, 且都是同一构造通式的机械实例化, 长文价值边际递减)。建议改用**两层文档结构**:

- **第一层(结构性长文, 少量)**: 针对**固定列**(company_listed_bank 20 个 + pair 长表 10 个 + company_tax_bank 对应固定列)与**加权测度通式本身**(`cw_X_t`/`ce_X_t` 构造法、8 权重版本、D12/D13/D17/D18 等设计决策)各写一篇长文, 规模约 30-50 篇, 与主项目"家族"概念对齐 —— 一个"家族"= 一种构造逻辑, 而非一个具体 (X, track, 权重) 组合。
- **第二层(继承引用)**: 具体 (X, track, 权重) 实例列在现有表格型 codebook 里, 通过"本列属于 XX 构造通式, 见长文 FSxx"的方式指回第一层, 不重复造文——**镜像主项目 codebook_longdesc 本身"一家族覆盖多 dta 短名列"的既有模式**(如政治词权重梯度、BERT 分布五族), 不是新发明。

若用户希望"每个具体列都要有独立长文", 则需另行拍板并重新估算规模(可能是数千篇量级, 工作量与主项目 655 篇不在一个数量级)。

⚠ **命名占位符声明**: 上文"FSxx"仅为示意性占位符, 尚非正式命名 SSOT。正式 ID 前缀/编号规则须在 P1 确定, 不得直接照搬主项目 `F0xx` 前缀(会与主项目家族编号空间产生视觉混淆, 即使物理目录不同)。

**核实结论(本轮复核, 好消息)**: 经逐条 grep 比对, D-系列决策编号(D4/D12/D16/D17 等)在 company_listed_bank 与 company_tax_bank 两份 codebook 中**语义一致、共享同一编号空间**(如两者的 D4 均指"自身即银行的排除口径"、D12 均指 `cw_X_t` 加权测度构造公式、D17 均指"消融预答/三义务段") —— 并非两套互相独立、需要费力对齐的编号体系, 这为 P1 新长文的交叉引用/术语统一提供了一个可直接复用的既有骨架, 无需额外调和工作。

⚠ **独立性原则的边界**: `company_bank_cooc_panel_codebook.md` 开篇明文声明"本 codebook 独立覆盖 company_listed_bank 流水线的全部产物 (与 news_process 主项目 codebook 相互独立, 互不交叉引用维护)"。本计划涉及的"复用主项目工具脚本/复用已核验 DOI 知识"属于**基础设施与知识复用**, 不等同于"内容层交叉引用"; 但为避免违反已声明的独立性原则, 第一层长文的正文内容**不得**以"参见主项目 F0xx"的方式建立跨项目内容依赖——如需引用同一构造逻辑, 应在侧线长文中独立完整复述, 而非指针式引用主项目文件。

## 3. 引用池策略

- **知识复用(只读)**: 优先参考主项目已核验的 **874-DOI 白名单**(尤其网络计量/共现测度/银企关系/shift-share 类, 与本侧线高度相关)作为文献线索, 避免重复检索。
- **工具复用(脚本, 已核实无需改造)**: `scripts/audit/check_longdesc_whitelist.py` 与 `admit_new_dois.py` 均已原生支持 `--longdesc-dir <DIR>` 参数(源码实读确认, 非推测: `check_longdesc_whitelist.py` 用 `--longdesc-dir` 定位 `_index.json`/`*.md`/`_new_dois_ledger.json`; `admit_new_dois.py` 同款), **P3 无需为多项目根参数化脚本** —— 此前 §6/§7 草稿中"是否需要参数化"的疑问已由代码核实解答: 不需要, 两侧线可直接复用现成脚本, 各传各的目录。
- ⚠ **P0 级别关键风险(本轮复核新发现, 必须先定案再动工)**: **绝不能**把侧线新增 DOI 写入主项目的 `config/codebook_longdesc/_new_dois_ledger.json`。主项目全局新颖度闸(`NOVELTY_YEAR_MIN=2023`, `NOVELTY_MIN_FRAC=0.50`)当前以 **50.02%** 的极小余量压线通过(见 memory `litanchor-supplement-*`/`prompt-assets-audit` 系列); 侧线主题(税调/工商登记/企业名称匹配/AKM 稳健标准误等)大概率会引入较多 2023 年之前的经典方法论文献, 若混入同一 ledger 参与同一比例计算, 极可能把主项目新颖度拉回 50% 以下, 导致**已收官、已推送**的主项目闸门重新报红——这是一个真实存在、后果严重且容易被忽视的耦合风险。
  **正确做法**: 每个侧线项目在其自身目录下建立**独立的** `_new_dois_ledger.json`(及配套 `_index.json`), 通过 `--longdesc-dir company_listed_bank/data/codebook_longdesc`(示意路径, 实际落点待 P1 定)运行 `admit_new_dois.py`/`check_longdesc_whitelist.py`, 使新颖度比例、白名单差集等**全部在侧线自身范围内独立计算**, 与主项目账本零交集、零耦合。跨项目共享的只是"已知安全的 DOI 线索列表"(人工参考), 绝不共享同一台账文件。
- 侧线特有主题走**独立 ledger** 下的 `admit_new_dois.py --scan-drafts`(Crossref 标题重叠 ≥0.6 + 撤稿筛查 + 五元组对抗复核)流程, 与主项目流程方法论一致但账本物理隔离。

## 4. 质量门槛

> ⚠ **2026-07-15 二次修订**: 字数门槛已由用户从"100字/1000字"扩充为**"1000字/5000字"**, 与主项目 standard/core 门槛(`≥1000`/`≥5000` CJK 汉字)**完全对齐、数字相同**。此前已按 100/1000 门槛撰写完成的 35 篇长文(LB 18篇 + TB 17篇)**全部需要扩充重写**方能达标, 详见新增 §8。

用户已明确给出两个字数门槛数字——**不少于 1000 字**与**不少于 5000 字**。以下二级分层是本计划对"两个数字如何对应到 standard/core 两级"的**推定映射**(依据: core 级承载结构性主干、理应门槛更高, 与主项目 core > standard 的相对关系一致), **该映射本身仍需用户在 P0 确认**, 不应被误读为用户已连带批准了分级方案:
- **standard 级(推定)**: 单篇 ≥1000 汉字。
- **core 级(推定, 结构性主干, 如固定列骨架、加权通式本身 `cw_X_t`/`ce_X_t` 构造法、权重双宇宙设计等)**: 单篇 ≥5000 汉字。
- 分级归属在 P1 变量清单固化阶段确定(镜像主项目 `_index.json::tier_by_col`); 门槛数字**现已与主项目 1000/5000 完全一致**(2026-07-15 二次修订前曾误用 100/1000, 已废弃)。
- 字数口径**沿用主项目既有惯例**: 按 CJK(中日韩统一表意文字)字符计数, 引文段落等英文/DOI 密集内容大量出现时不计入正文字数(镜像主项目 memory 中"引文段汉字≈0不计入→段落下限中文正文独立过线"的既有做法), 避免大段英文引用注水凑字数。
- ⚠ **"引用 ≥3 条/篇"待核实**: 此前草稿写"引用 ≥3 条/篇, 全部来自白名单或经 admit 流程核验"——经本轮源码复核, `check_longdesc_whitelist.py` 中确认存在的是**引用来源合法性闸**(citations 必须在白名单差集为空)与新颖度占比闸, 未在本次复核中定位到"每篇最低 3 条"的显式数量下限常量。"≥3 条"更可能是历次会话对主项目**典型实践**的经验描述, 而非代码强制的硬阈值。**结论**: 数量要求保留为**建议性目标**(≥3 条较扎实), 但不作为本计划的硬性验收标准写入, 避免制定一条实际不存在的"假门槛"、日后验收时产生名实不符的争议; 若用户希望设为硬性下限, 需在 P0 一并明确并在侧线专属校验逻辑中显式实现(因为共享的 `check_longdesc_whitelist.py` 本身未内置该数量闸)。
- 人工中文正文区(`## CORE`/等价段)零 markdown 加粗、零裸 DOI URL、零集合记号 `{}` ——**直接复用本轮修复过的 `_stata_notes_text()` 教训**, 若这两个侧线未来也要走 Stata notes 注入, 提前规避同类 `/*`/`{}` 崩溃。

## 5. 是否需要 Stata notes 实机注入

两侧线的 `.dta` 产物(`company_bank_cooc_panel.dta` 等)当前**没有**逐列 notes/label 元数据注入需求的既有先例(README/codebook 未提及); 是否需要镜像 WP5 的实机注入步骤应作为**独立子决策**, 不默认纳入本计划 — 先完成文档层, 注入层留待用户后续单独批准。
