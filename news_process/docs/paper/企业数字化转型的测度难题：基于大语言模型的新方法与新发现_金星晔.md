【角色设定】
你是一位顶尖的学术评审与项目操盘专家，精通理论框架推演与实证金融学项目落地。输出要求极致精简、直击痛点、逻辑严密。

=========================================
第一部分：基于参考论文的项目分析与诊断报告

1. 范式映射与盲区诊断
参考论文《企业数字化转型的测度难题：基于大语言模型的新方法与新发现》的核心机制在于：传统词典法存在严重的“第一类错误（漏判）”和“第二类错误（误判，如未来意图、行业背景等）”，大语言模型（如ERNIE）能有效解决该问题。更为关键的是，论文揭示了显著的“技术异质性”——大数据、人工智能、云计算、物联网、移动互联能提升财务绩效（ROA/ROE），而**区块链技术并未产生显著积极作用**。同时，数字化转型发挥作用的渠道主要在于“提高效率（TFP）”和“降低成本”，而非单纯“增加收入”。

当前项目的盲区诊断：
- **分类颗粒度落差**：当前 `config.yaml` 中 LLM 的输出仅提取泛化的 `fintech_topic` 及二元论的 `fintech_category`（底层技术/应用场景），未能精准拆分上述六大类数字技术，导致后续无法直接对齐论文中“区块链无效 vs. 其他技术有效”的异质性检验。
- **时态筛选缺失**：当前阶段一的“实质关联”识别条件中包含“战略部署”，容易导致将大篇幅阐述的“未来的数字化转型意愿或计划”计入当期指标。这与参考论文中必须剔除“未发生的未来意愿”原则相背离。
- **因果机制断层**：目前的面板构建仅停留在情绪指标合并生成层面，缺乏专门对应 TFP（效率渠道检验）及成本收入比的中介变量，实证闭环仍显薄弱。

2. 实质性改进项（宁缺毋滥）
- 改进 A：在 LLM 输出的 JSON 范式中废除模糊分类，新增 `tech_subtypes` 数组，明确提取并归类至六大基本技术节点（大数据、人工智能、云计算、物联网、移动互联、区块链）。
  -> 标明论文依据：参考论文实证发现区块链（BC）回归系数不显著，而其他五项显著。因此必须建立并行的六类独立指标。
  -> 阐述预期边际贡献/解决的内生性问题：支持细微颗粒度的技术异质性回归体系，规避将无效技术（区块链炒作）与有效硬技术（AI/云计算）混为一谈引发的均值掩盖效应，精准界定异质性边界。

- 改进 B：全面修订 LLM Prompt 的“实质关联”过滤防线，强制要求“剔除纯战略愿景、未来计划等未发生事件，仅保留当前已落地或取得实质进展的数字化应用”。
  -> 标明论文依据：论文明示，第二类错误的核心成因往往包括“可能表示将在未来进行数字化转型而不是现在”。
  -> 阐述预期边际贡献/解决的内生性问题：最大限度降低测量误差（Measurement Error），严格避免企业画大饼或“洗绿”行为带来的提前入表干扰，增强指标的当期约束力。

- 改进 C：在面板输出配置（Data Aggregation）阶段，将全要素生产率（TFP）和成本收入比（Cost-to-Income Ratio）正式明确为必须核算和保存的通道验证变量。
  -> 标明论文依据：该论文证实金融数字技术主要通过两条渠道（改善效率、降低成本）发挥作用，否决了收入驱动假设。
  -> 阐述预期边际贡献/解决的内生性问题：完整闭合因果检验微观路径，为机制检验（Mechanism Check）提供确凿弹药。

3. 冗余剥离
- **伪需求：泛化类别（fintech_category）**。将金融科技硬分为"底层技术"与"应用场景"难以在微观财报实证中体现统计学上的异质性意义，且增加了大模型的鉴别压力，建议直接重构和剔除，代之以具体的强关联技术类别列表。
- **伪需求：词典法中的“前瞻性陈述词汇集”（forward_looking_words）**。在后续大模型全量覆盖且 Prompt 内置了时点判定动作的前提下，仅依靠词面权重倒逼判断易造成混淆甚至相悖的结果，剥离传统时态词表以降低算力与分析冗余。

=========================================
第二部分：项目重构与优化执行计划书

1. 优先级排布
【速赢项（Quick Wins）】：
- 修改 `config.yaml` 中阶段21的 Prompt 模板：剥离 `fintech_category` 字段，插入 `tech_types` (枚举型列表)输出格式约束。
- 原地强化 Prompt 判断规则，新增严格过滤未来战略/倡议书类文本的时态铁律。
【核心攻坚项】：
- 拓展面向银行层面的 TFP 收敛测算及成本效用函数构建。

2. 阶段化执行指令 (SOP)

阶段一（机制重塑/数据清洗）：
- **核心动作指令**：
  进入 `config.yaml` 覆写 `prompt_template`，在 `<step1_verification>` 区域补充：“必须是正在实施、已落地应用或取得实质性进展的金融科技项目。纯未来畅想、远期规划与口号宣传判定为 false。”
  修改 `<output_format>` 的 JSON 原则，将 `fintech_category` 更名为 `core_tech_type`，设定值为：“只能从[大数据, 人工智能, 云计算, 移动互联, 物联网, 区块链, 综合未明确]中挑选匹配的最强相关类别列表。”
- **交付物标准**：更新后的 `config.yaml` 保证跑出的 `.parquet` 精准识别各类底层技术流派及摒弃预期污染资讯。

阶段二（实证/模型重构与检验）：
- **核心动作指令**：
  在面板拼装的回归框架环节，明确拉取各银行当期的[业务及管理费/营业收入]计算成本收入比（Cost Channels）；运用传统LP或者ACF半参数方法进行银行特质 TFP 估算。
  在主效应回归池中，将单一数字化转型 dummy 变更为六大技术的独立哑变量进行联合入模。
- **稳健性检验标准**：剔除极端绩效的尾部样本。并复现针对“高维金融科技投入反而推升收益风险弹性”的假说讨论。

阶段三（结论重构）：
- **核心动作指令**：
  实施基于原 ROA 所处低中高不同分位点（10%、50%、90%）的分位数回归（Quantile Regressions）。检验在城商行/农商行（低基础群体）中数字化转型的“雪中送炭”补药作用，对标国有大行的“锦上添花”效应。

3. 风险预案 (Plan B)
- 致命卡点：银行层级投入要素高度同质化（资本与劳本等）或不可度量导致 ACF 估计 TFP 时出现异常跳变或拒收敛。
  -> 替代方案（Plan B）：放弃复杂的 TFP 构筑，退而求其次仅用“净成本收入控制率”、运营人效等直观财务比率锚定其效率改善渠道。
- 致命卡点：LLM 对涉及复合技术的语句（例如“基于云计算的大数据AI平台”）产生幻觉，从而返回非标准化分类引发 JSON 解析失败。
  -> 替代方案（Plan B）：在 JSON 反序列化解析器（`21_tone_llms.py`）处加入容错强转机制：只要包含相应核心词簇即打上对应技术类型的 dummy tag，允许多标签并立（Multi-label），而非强制其输出唯一分类。
