一、项目一句话总结¶

本项目把 2007–2024 年间约 40 万条中文财经新闻，转换成 1,771 家中国银行 × 18 年的银行-金融科技互动面板数据集，并支撑 11 篇拟投顶刊与 CSSCI 的实证论文。

把这句话拆开看，就是三件事：

三件事 通俗解释 学术对应
抓什么 中国银行业 + 金融科技相关的中文新闻 文本数据采集（已完成）
抽什么 谁、谈论谁、用什么口吻、是不是有政策意图、是不是从众跟随… 文本→变量的"测度层"
回答什么 媒体关注/语调/分歧/陈旧度 → 银行风险承担、绩效、战略差异化 因果识别（DiD / IV / RDD …）

简言之：前 60% 的工作量是把"文字"翻译成"数字"，后 40% 的工作量是把"数字"喂给 Stata 写论文。

二、研究问题：为什么要花这么大力气做这件事？¶

经济学和金融学的传统数据（资产负债表、股价、监管披露）是"硬指标"。但很多重要的经济行为是先在新闻里浮现，再在数据里成形的：

  • 一家银行被媒体集中报道金融科技战略之前，它的科技投入比例往往还没有跳变；
  • 媒体对同一家银行的口径分歧，常常是分析师私下信息打架的外泄；
  • 一篇财经稿子如果长期重复使用旧短语（陈旧度高），意味着信息环境正在恶化；
  • 行业从众（herd）行为在监管报表里几乎看不到，但在新闻语调的"同步性"中清晰可见。

这些都是软指标——藏在文字里、有理论意义但传统数据库不收录。本项目的核心价值就是：用一套可复现、有计量学验证、跑得动顶刊的工作流，系统地把这些软指标做出来。

教授视角的一句话：如果说传统实证经济学是用"望远镜"看资产负债表，本项目是用"显微镜"看新闻文本。两者结合，才能解释 2017 年以后中国银行业的真实变化轨迹。

三、数据全景：从新闻到面板的三段旅程¶

整条流水线的"数据物理形态"演化如下：

┌─────────────┐    ┌──────────────────┐    ┌────────────────┐    ┌─────────────┐
│ 原始新闻 .xlsx│ →→ │  按文章打标的 .parquet  │ →→ │ 银行×年的 panel │ →→ │ Stata .dta  │
│  40 万条     │    │ （每条新闻一行，含语调、 │    │  (84×2 或 N×T) │    │（IC/SE/MP）│
│  2007-2024  │    │  关注度、政策对齐等 30+ 列）│    │  ~2,000 列    │    │             │
└─────────────┘    └──────────────────┘    └────────────────┘    └─────────────┘
   data/raw/         data/processed/*.parquet                       *.dta

3.1 输入侧：原始新闻¶

  • 来源：60+ 中文财经媒体的历史抓取（财新、21 世纪经济报道、第一财经、新浪财经…），合并去重后约 40 万条；
  • 存放：news_process/data/raw/*.xlsx，每条带"标题、正文、发布日期、媒体名"；
  • 银行清单：news_process/config/bank_list.yaml，frozen 在 2024-Q4，共 1,771 家（国有 6 + 政策性 3 + 央行 1 + 股份制 12 + 城商 124 + 农商 1563 + 民营 19 + 外资 41 + 直销 2）。这份清单是项目所有"提及"判断的锚。

3.2 中间产物：每个 stage 各下一颗"蛋"¶

流水线一共 20 个生产 stage（外加 17 个验证 stage），每一个 stage 跑完都会在 data/processed/ 留下一个 .parquet 文件——这是项目最重要的工程纪律之一：

  • ✅ 任何一步出错，从那一步接着跑就行，不用从头来；
  • ✅ 任何中间产物都可以用 pandas 直接打开检查；
  • ✅ 测试就是"对比当前 parquet 与黄金基线的列哈希"——精确到列。

目前 data/processed/ 累计约 9 GB、198 个 parquet 文件，记录了 653 次完整 run。

3.3 输出侧：可以喂给计量模型的面板¶

最终产物只有一个：data/processed/40_panel_yearly.parquet，再由 stage 46 切成三个 .dta：

.dta 文件 列数 给谁用
46_panel_yearly_core.dta 49 列 外部协作者 Stata IC（≤2048 变量上限）兼容入口
46_panel_yearly_aux.dta 1977 列 与 core 互补，1:1 merge 可还原 full
46_panel_yearly_full.dta 2024 列 本机 Stata MP 直接用

教授提醒：列数膨胀到 2000+ 不是因为模型变量多，而是因为每个软指标都做了多种变体（dictionary 版、LLM 版、BERT 版；全文版、上下文版；不同温度、不同提示词…）做稳健性。真正进主表的核心解释变量通常只有 1–3 个，其余都是 robustness 子军。

四、流水线一览：20 个 stage 的故事¶

整条 pipeline 在 news_process/core/dag.py 里用一个 Python 列表声明（这就是所谓"declarative DAG"）。每个 stage 对应仓库根下一个 NN_xxx.py 入口（叫 thin shim，每个不超过 30 行，只负责"调用业务函数"，业务逻辑都在 pipeline/ 子包里）。

下面按"故事线"分四幕讲，把 20 个 stage 的来龙去脉串起来——只看一遍，就能记住整条线的形状：

第一幕：清洗与归属（00 → 11 → 12 → 13）¶

  • 00_preprocessing：去 HTML 标签、统一编码、去重、删空标题。
  • 11_news_bank：判断"这条新闻是不是讲银行的？讲哪家？" 用 bank_keywords.json + Aho-Corasick 多模式匹配。
  • 12_news_fintech：判断"这条新闻有没有提金融科技？" 用 fintech_dict.json。
  • 13_materialize_ctx（v3.6.0 新增）：把"提及银行名"周围 ±N 个 token 的窗口切出来，存成新列 content_ctx。
  • 为什么要切？因为一篇报道可能既提工商银行又提"区块链概念"，但两件事在文章里隔了 1000 字；如果只看全文，会误以为"工商银行在做区块链"。_ctx 列只取局部窗口，避免归因污染。这就是后面会反复出现的"双轨（full vs ctx）"思想的源头。

第二幕：变量构造（14 → 15 → 17 → 18 → 19）¶

  • 14_fintech_intensity：金融科技在某银行某文章中的强度（关键词密度 × 文章长度调整）。
  • 15_article_policy_alignment：文章语义与"金融政策语料"的余弦相似度（用 OpenAI embedding）。
  • 17_article_topic：BERTopic 主题建模（D 组功能，v3.7.0 新加）。
  • 18_article_staleness：文章"陈旧度"——它跟同期同源文章的相似度（信息环境质量代理）。
  • 19_executive_ner：LLM 抽取 CEO/高管命名实体（v3.7.0 D4 新加）。

第三幕：情感测量（21 → 22 → 23 → 24）¶

这是项目最核心的方法学创新——三种独立路径同时做情感分析：

Stage 方法 优点 缺点 在论文中的角色
21_tone_llms LLM 投票（yunwu API，多模型多温度） 语义理解最强 贵、不稳定、有"幻觉" 主分析
22_tone_words LM 2011 JF 词典（含 v3.5.2 新加的 4 子词典） 透明、可复现、零成本 词典覆盖差、忽略否定 基线对照
23_tone_berts 5 种 BERT 模型（含 FinBERT2、IDEA-CCNL 等） 语义+复现性折中 需 GPU、模型黑盒 方法学稳健性
24_herd_decay_processor 时间衰减加权 + 同业从众权重 解决"刚发布的新闻 vs 旧新闻同等加权"问题 参数敏感 行业网络效应

教授提醒：审稿人一定会问"你们怎么知道 LLM 不是在乱编？"——这正是为什么我们要同时跑三套。如果三套口径在主回归里方向一致、显著性接近，故事才站得住。23 和 22 在论文里是给审稿人写 robustness table 的护身符。

第四幕：聚合与导出（30a / 30 / 31 / 32 / 45 / 46 / 49 / 51 / 53）¶

  • 30a_article_sbert & 30_robustness_text2vec：把每篇文章打成 sentence embedding，供后续 BERTopic / 相似度 / 媒体多元化等用。
  • 31_bank_fintech_threshold & 32_news_llms_human：阈值校准 + 人工标注比对（一部分输入留给 D-day 校准）。
  • 45_panel_export_main：把所有文章级特征按 (银行, 年) 聚合为最终 panel。这一步决定了"一篇文章上的指标，到银行-年 panel 上变成什么形式（均值？最大值？加权？）"。
  • 46_stata_export：把 panel 切成 core / aux / full 三个 .dta，让 IC、SE、MP 三类 Stata 用户都能跑。
  • 49_risk_taking_outcomes：构造下游结果变量——风险加权资产比、NPL formation、LLP 自由裁量等（用于 P10/P11）。
  • 51_falsification_test：placebo & falsification 测试，确认主回归不是偶然显著。
  • 53_export_stats_excel：导出描述性统计供论文 Table 1。

验证子流水线（32a / 38a / 38b / 39a / 39c / 39d / 39e / 39f）¶

带字母后缀的 stage 都是验证/稳健性专用，不进主流水线：

  • 32a_dedup_threshold_sensitivity：去重阈值敏感性
  • 38a_temporal_mask_test / 38b_decay_sensitivity：时间窗 / 衰减系数稳健性
  • 39a_inter_track_kappa：三轨情感 Cohen's κ 一致性
  • 39c_construct_orthogonality：构念正交性（HTMT）
  • 39d / 39e：词典/LM 区分效度
  • 39f_cross_media_alpha：跨媒体 Krippendorff α 一致性

它们的存在告诉审稿人：我们不是凭空相信自己的指标，每个核心构念都经过了独立校验。

五、几个必须先理解的核心概念¶

下面 4 个概念会反复出现在代码、配置、论文里——先认识它们，后面才看得懂。

5.1 双轨设计：_full vs _ctx¶

很多变量名带 _full 或 _ctx 后缀：

  • _full = 用整篇文章计算的版本
  • _ctx = 只用"银行提及附近上下文窗口"计算的版本

为什么要两个？——一句话：_full 对"整体语调"敏感（涵盖范围大但容易污染），_ctx 对"针对该银行的具体表达"敏感（精准但样本小）。两者方向一致才有故事，方向冲突也可以单独立项（这正是 P11 bank_news_clarity 的研究问题）。

主回归里到底用哪个，由每篇 paper 的 paper_spec.yaml 决定。v3.6.0 起，P1 bank_fintech_tone 的 main 切到了 _ctx。

5.2 三轨情感：LLM × Dictionary × BERT¶

如上一节所述，主回归用 LLM，但论文表里永远会附上词典/BERT 版作 robustness。审稿人一旦质疑 LLM 的可靠性，我们立刻能掏出两个独立证据。

5.3 Thin shim 工程纪律¶

仓库根目录下有 39 个 NN_xxx.py 文件——每一个都不超过 30 行。这是刻意的：

# 例：21_tone_llms.py（伪代码示意）
from news_process.pipeline.sentiment.tone_llms import main
if __name__ == "__main__":
    main()

规矩：业务逻辑一律放 news_process/pipeline/ 下的对应模块。原因有三： 1. 测试只测 pipeline 模块，shim 不进单元测试； 2. 单个 stage 可以独立 python 21_tone_llms.py 调试； 3. DAG 编排器把每个 shim 当成独立子进程跑——一个 stage 崩了不会污染其他 stage 的内存。

5.4 SSOT（Single Source of Truth）¶

四个权威源——任何变更都要让它们保持一致：

权威源 位置 决定了什么
DAG core/dag.py::STAGES_MAIN 流水线由哪些 stage 组成、按什么顺序跑
OUTPUT_REGISTRY core/schemas.py::OUTPUT_REGISTRY 每个 stage 产出哪些 parquet 列
拆分 YAML config/{paths,preprocessing,filtering,sentiment,features,panel,validation}.yaml 所有可调参数
Python 依赖 pyproject.toml::[project].dependencies 整套环境的版本锁

任何一处改动都有对应的 integration test 守门（tests/integration/test_dag_consistency.py 等）。

七、Stata 层：把 panel 变成论文¶

Python 流水线只到 46_stata_export。从这里往后，全是 Stata 的天下。

7.1 本机 Stata 环境¶

  • 版本：StataNow/MP 19.5（64 核 / 128 GB RAM）
  • 路径：C:\Program Files\StataNow19\StataMP-64.exe
  • policy：项目策略锁定 Stata 19+；91 个 .do.tmpl 模板统一用 version 19 头部，外部协作者必须升级。

7.2 模板生成机制¶

不要手写 .do 文件。运行：

python -m news_process.papers._common.stata_runner build-replication

它会把 14 个主模板 + 各 paper 的 5-8 个 paper-specific 模板（共 102 个 .do.tmpl）按 paper_spec.yaml 里的占位符替换，生成可执行的 replication 包。

7.3 主表"M1→M6 递进控制"约定¶

所有 paper 的核心 Table 2 都遵循以下递进结构（这是经济学顶刊的通行做法）：

列 内容
M1 OLS 裸回归
M2 + 银行 FE
M3 + 年 FE
M4 + 银行 × 年双向 FE（reghdfe）
M5 + 控制变量
M6 + IV / DID / RDD / sdid（识别策略）

读者一眼看过去就知道：从 M1 到 M6，系数稳不稳。

7.4 稳健性矩阵¶

每篇 paper 配套至少 5 类稳健性：

  1. wild bootstrap（boottest）—— 处理 cluster 数过少
  2. randomization inference（ritest）—— treatment 随机化重排
  3. rwolf—— 多假设检验 family-wise error rate
  4. honestdid —— DID 的平行趋势 sensitivity
  5. bacondecomp —— 交错 DID 的"恶毒比较"诊断

如果一篇 paper 跑不出 5 类稳健性，要么是数据问题，要么是设计问题——审稿人会闻到。

8.4 日志¶

每次跑流水线都会创建一个 run_id，日志放在：

logs/runs/<run_id>/<stage>.log

任何 stage 失败，第一时间查它的 log。日志格式统一，含 stage 开始 / 结束时间戳、关键指标、异常 traceback。

十、常见疑问 FAQ¶

Q1：项目这么大，从哪开始读？¶

推荐顺序：

  1. 本简明版（你现在在读的这份）
  2. CLAUDE.md（顶部 "Current version" 段，看最新动态）
  3. core/dag.py（看 STAGES_MAIN 列表，建立 stage 全景）
  4. 挑一个你感兴趣的 paper，读它的 paper_spec.yaml + analysis.py
  5. 再去看 pipeline/ 里相应的业务模块
  6. 最后才看 PROJECT_DESCRIPTION.md（白皮书）查细节

Q2：为什么要把流水线拆这么细？¶

主要是三个原因： - 可复现：每个 stage 一个 parquet，任何一步出问题都能从中间接着跑。 - 可解耦：审稿人质疑某个变量，我们只需要重跑那一个 stage，不动其他。 - 可验证：每个 stage 都有专门的 pytest 文件，覆盖 1,700+ 个 fast test。

Q3：双轨（full vs ctx）哪个对？¶

两个都对，但回答不同的问题： - 想知道"媒体整体氛围"→ 用 _full - 想知道"针对这家银行的具体表达"→ 用 _ctx

主回归用哪个，由 paper_spec.yaml 决定，且要在论文 Section 3 明确交代选择理由。

Q4：LLM 调用要花多少钱？¶

  • 全跑一次 stage 21 + 34 + 36 + 39 ≈ 几十美金到上百美金量级（取决于模型选择和样本量）
  • 所有 LLM 输出都被 archive 到 append-only JSONL（v3.7.0 DC3 模块），SHA-256 manifest 保证可复现
  • 词典版（stage 22）和 BERT 版（stage 23）零成本，是 LLM 不可用时的 fallback

Q5：FinBERT2 模型本地没有怎么办？¶

stage 23 会自动跳过——其他 4 个 BERT 模型仍跑。不阻塞流水线。

Q6：测试报错"import torch 失败"怎么办？¶

这是已知问题。CI 有 5 个 job 矩阵，其中 4 个 light job 没装 torch。新加的测试如果用了 torch，必须在文件顶加：

import pytest
pytest.importorskip("torch")

否则 4 个 light job 全红。（见 MEMORY.md::ci_matrix）

Q7：可以删掉某个 stage 吗？¶

不要随便删。任何 stage 的删除/添加都要： 1. 改 core/dag.py::STAGES_MAIN 2. 改 core/schemas.py::OUTPUT_REGISTRY 3. 跑 pytest tests/integration/test_dag_consistency.py 4. 如果改变了 panel 列 schema，重新生成 golden baseline

Q8：commit 规范？¶

  • 永远不要 amend 已有 commit（pre-commit hook 失败后要建新 commit）
  • 不要 git add . 或 git add -A，逐文件加，避免误提交 .env
  • commit message 末尾加：Co-Authored-By: Claude Opus 4.7 (1M context) <noreply@anthropic.com>
